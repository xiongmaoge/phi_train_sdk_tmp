> 文档版本：v1.0 ｜ 日期：2026-09-18 ｜ 状态：设计稿（骨架已落地，标注 TODO 的部分为待实现）

## 1. 项目背景

### 1.1 定位

`phi_train_slurm` 是**训练 infra SDK**：在 **EHPC-Slurm 集群**上提交、查询、管理**具身 VLA（Vision-Language-Action）模型预训练作业**，面向内部团队使用。

与数据侧 SDK 的分工：

| 仓库 | 职责 |
| --- | --- |
| `phi_data_sdk` | 数据预处理、OSS → CPFS 数据同步（phi-sync，NAS 数据流动 OpenAPI） |
| `phi_train_slurm`（本仓库） | 训练任务提交到 Slurm、状态查询、日志拉取、取消、故障自动续训 |

### 1.2 目标

1. 让算法同学**不直接接触 Slurm 命令**（sbatch/squeue/sacct），用声明式 YAML + 少量 CLI/Python API 完成训练作业全生命周期管理。
2. 支撑**百卡级（8+ 节点）多机预训练**：gang scheduling、多机启动、日志可查、故障可自愈。
3. 保持与 `phi_data_sdk` 一致的工程约束：**零运行时依赖**、纯 Python wheel 自包含、离线可测。

### 1.3 术语

| 术语 | 说明 |
| --- | --- |
| JobSpec | 作业声明式配置（YAML/代码），描述训练任务长什么样 |
| SlurmBackend | Slurm 交互唯一出口，封装 sbatch / squeue / sacct / scancel |
| JobHandle | 已提交作业的操作句柄：wait / logs / cancel |
| requeue | 故障自动重提交（Slurm 不原生支持自动续训，由 SDK 实现） |
| CPFS | 并行文件系统：训练数据、checkpoint、日志的存储 |

## 2. 需求分析

### 2.1 功能性需求

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| FR-1 | 作业提交 | 声明式配置 → 生成 sbatch 脚本 → 提交到 Slurm，返回 job id |
| FR-2 | 多机训练 | 支持 N 节点 × M 卡；每节点 1 个 srun 任务，内部 torchrun/deepspeed 拉起 M 个 GPU 进程 |
| FR-3 | 容器化 | 支持 pyxis/enroot 容器镜像与挂载（CPFS 目录映射进容器） |
| FR-4 | 状态查询 | squeue/sacct 状态归一为统一 JobStatus |
| FR-5 | 日志拉取 | 日志落 CPFS，登录节点可读，支持 follow |
| FR-6 | 作业取消/占位 | cancel / hold / release |
| FR-7 | 故障自动续训 | 检测 NODE_FAIL 等可重试失败，自动重提交并从 checkpoint 续训 |
| FR-8 | 提交前校验 | 作业名/资源/命令合法性 + 挂载路径存在 + 数据集非空 |

### 2.2 非功能性需求

| 编号 | 需求 | 设计决策 |
| --- | --- | --- |
| NFR-1 | 零运行时依赖 | SSH 走系统 `ssh` 命令（subprocess），不走 paramiko；pyyaml 为可选 extra |
| NFR-2 | 离线可测 | 纯数据/纯字符串部分（校验、状态映射、脚本渲染）不连集群即可单测 |
| NFR-3 | 密钥安全 | 环境变量注入 `${VAR}` 提交时从本地展开，密钥不进 YAML 不进仓库 |
| NFR-4 | 可序列化 | JobSpec 支持 to_dict/from_dict，requeue 重提交与模板共享保持一致 |
| NFR-5 | 状态可脚本化 | CLI 输出可直接被 shell 取用（不带 `--wait` 只输出 job id 等） |

## 3. 总体架构

### 3.1 核心抽象

```
JobSpec (声明式配置)  →  SlurmBackend (执行器)  →  JobHandle (作业句柄)
  YAML 描述训练           sbatch/squeue/sacct        wait / logs / cancel
  长什么样                唯一碰 Slurm 的地方         操作一个已提交作业
```

分层职责：

| 层 | 模块 | 职责 |
| --- | --- | --- |
| 用户接口 | `submitter/`（CLI `phi-train`） | 命令行 + SDK 入口函数 |
| 作业编排 | `job/manager.py`、`job/handle.py` | spec → script → 提交；wait/requeue/logs/cancel |
| 集群交互 | `slurm/backend.py` | SSH + Slurm 命令封装（唯一出口） |
| 脚本生成 | `slurm/launcher.py` + `templates/` | 启动命令与 sbatch 脚本渲染 |
| 数据模型 | `model/`、`job/job_spec.py`、`job/status.py` | 纯数据结构与状态映射 |

### 3.2 目录结构

```
phi_train_slurm/
├── README.md                  # 使用说明

│   ├── job_spec.py            # JobSpec + RequeueConfig + YAML 解析 + 校验
```

## 4. 数据模型设计

### 4.1 ResourceSpec（Slurm 资源申请）

字段与 sbatch 指令一一对应：

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `partition` | str | `"gpu"` | Slurm 分区 |
| `qos` | str \| None | None | QOS，None 时不生成指令 |
| `nodes` | int | 1 | 节点数（多机时由 Slurm 保证 gang scheduling） |
| `gpus_per_node` | int | 8 | 每节点 GPU 数 → `--gres=gpu:N` |
| `cpus_per_task` | int | 16 | 每 srun 任务 CPU 核数 |
| `mem_per_node_gb` | int \| None | None | 每节点内存上限（GB），None 不限制 |
| `time_limit` | str | `"72:00:00"` | 最长运行时间，超时 Slurm 终止 |

### 4.2 JobSpec（作业声明式配置）

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `job_name` | str | 必填 | 作业名（`[A-Za-z0-9_-]+`），查询/日志定位主键 |
| `resource` | ResourceSpec | 必填 | 资源申请 |
| `command` | str | 必填 | 训练命令（SDK 自动包成 srun+torchrun） |
| `image` | str \| None | None | pyxis 容器镜像；None 用宿主机环境 |
| `mounts` | list[str] | [] | `host:container` 挂载，host 为 CPFS 路径 |
| `env` | dict | {} | 环境变量；值含 `${VAR}` 时提交时从本地展开 |
| `launch_backend` | str | `"torchrun"` | `torchrun` \| `deepspeed` |
| `log_dir` | str | `"/mnt/cpfs/logs"` | sbatch 输出/错误日志目录（CPFS） |
| `requeue` | RequeueConfig | 默认启用 | 故障自动重提交配置 |

**校验规则（validate()）**：作业名合法、`nodes/gpus_per_node ≥ 1`、command 非空、launch_backend 白名单。

**RequeueConfig**：

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `enabled` | True | 是否启用自动重提交 |
| `max_retries` | 3 | 最大重试次数 |
| `resume_from` | None | checkpoint 目录；训练代码契约：存在则续训 |

### 4.3 JobStatus（状态机）

统一状态（`str` 子类枚举，带 `is_terminal()`）：

| SDK 状态 | 含义 | 是否终态 |
| --- | --- | --- |
| `SUBMITTED` | sbatch 已返回 job id | 否 |
| `PENDING` | 排队中 | 否 |
| `RUNNING` | 运行中 | 否 |
| `SUCCEEDED` | 正常完成 | **是** |
| `FAILED` | 失败（含 NODE_FAIL/TIMEOUT/OOM） | **是** |
| `CANCELLED` | 用户取消 | **是** |
| `REQUEUED` | 被抢占/重排队（内部容错状态） | 否 |

**Slurm 原始状态 → SDK 状态归一映射**：

| 来源 | Slurm 原始状态 | SDK 状态 |
| --- | --- | --- |
| squeue（运行中） | PENDING / CONFIGURING / RESV_DEL_HOLD / SUSPENDED / STOPPED | PENDING |
| squeue | RUNNING / COMPLETING | RUNNING |
| sacct（已结束） | COMPLETED | SUCCEEDED |
| sacct | FAILED / NODE_FAIL / OUT_OF_MEMORY / OOM / TIMEOUT | FAILED |
| sacct | CANCELLED / REVOKED | CANCELLED |
| sacct | PREEMPTED / REQUEUED | REQUEUED |

**可重试状态**（requeue 判定依据）：`FAILED / NODE_FAIL / OUT_OF_MEMORY / OOM / TIMEOUT / PREEMPTED / REQUEUED`。用户主动取消（CANCELLED）**不**重试。

## 5. 核心模块设计

### 5.1 slurm/launcher.py —— 脚本生成

**多机启动命令**（标准 GPU 训练模式：sbatch 侧 `--ntasks-per-node=1`，节点内由框架再拉起进程）：

```
# torchrun
srun --label torchrun --nnodes=$SLURM_NNODES --nproc_per_node={G} \
     --rdzv_endpoint=$MASTER_ADDR:29500 {command}

# deepspeed
srun --label deepspeed --num_nodes=$SLURM_NNODES --num_gpus={G} {command}
```

**sbatch 指令头生成规则**（有条件的指令在代码里拼，模板只放脚本体）：

| 条件 | 生成指令 |
| --- | --- |
| 恒有 | `--job-name` / `--partition` / `--nodes` / `--ntasks-per-node=1` / `--gres=gpu:N` / `--cpus-per-task` / `--time` |
| `qos` 非空 | `--qos` |
| `mem_per_node_gb` 非空 | `--mem`（GB→MB） |
| 恒有 | `--output/--error = {log_dir}/{job_name}-%j.out/.err`（日志落 CPFS） |
| `image` 非空 | `--container-image`、`--container-mounts`（mounts 逗号拼接） |

**模板渲染**：占位符替换（`$env_exports` / `$master_port` / `$command`），模板中的 `$SLURM_*` shell 变量保留原样。

### 5.2 slurm/backend.py —— SlurmBackend

所有 Slurm 命令经登录节点 SSH 执行。命令约定：

| 操作 | 命令 | 说明 |
| --- | --- | --- |
| 提交 | `sbatch <script>` | stdout：`Submitted batch job 12345` |
| 运行中状态 | `squeue -j <id> -h -o %T` | 快，仅队列内可见 |
| 终态 | `sacct -j <id> -n -P --format=State,ExitCode` | 含退出码 |
| 取消 | `scancel <id>` | — |
| 占位/放行 | `scontrol hold/release <id>` | — |

方法清单：

| 方法 | 状态 | 说明 |
| --- | --- | --- |
| `_run(remote_cmd, timeout)` | TODO | subprocess 调系统 `ssh`，非零退出抛 SlurmError |
| `submit(script)` | TODO | 上传脚本 + sbatch + 解析 job id |
| `status(job_id)` | TODO | squeue 优先、sacct 兜底、按映射归一 |
| `cancel / hold / release` | TODO | 对应 Slurm 命令 |
| `read_log(path, tail, follow)` | TODO | SSH tail，follow 持续输出 |
| `path_exists / dir_nonempty` | TODO | 提交前 sanity check |

**状态查询优先级**：squeue 命中 → 用 squeue 映射；否则查 sacct；两者都无 → `UNKNOWN`。

### 5.3 job/manager.py —— SlurmJobManager

对上层暴露的作业管理入口（与 phi_data_sdk 的 JobManager 同构：只做编排，交互全委托 backend）。

**提交流程**：

```
1. spec.validate()                      # 作业名/资源/命令合法性
2. sanity check                         # mounts host 路径存在 + 数据集目录非空
3. render_sbatch_script(spec)           # 生成脚本
4. backend.submit(script)               # 提交，解析 job id
5. 返回 JobHandle
```

### 5.4 job/handle.py —— JobHandle

| 方法 | 说明 |
| --- | --- |
| `wait(timeout, poll_interval)` | 轮询直到结束；命中可重试失败时自动 requeue（见流程 6.3） |
| `logs(follow, tail)` | 读 CPFS 日志（`{log_dir}/{job_name}-{job_id}.out/.err`） |
| `cancel()` | scancel |

### 5.5 submitter —— CLI 与配置

| 命令 | 说明 |
| --- | --- |
| `phi-train submit exp_vla.yaml [--wait] [--username <name>]` | 提交；`--wait` 阻塞到终态，不带则立即返回 job id |
| `phi-train status <job-id>` | 只输出状态字符串（便于脚本取用） |
| `phi-train logs <job-id> [--no-follow] [--tail N]` | 拉日志，默认 follow |
| `phi-train cancel <job-id>` | 取消 |

连接配置（环境变量优先，`.env` 兜底，已存在环境变量不被覆盖）：

| 环境变量 | 说明 |
| --- | --- |
| `PHI_SLURM_HOST` | 登录节点地址（必填） |
| `PHI_SLURM_USER` | SSH 用户 |
| `PHI_SLURM_IDENTITY_FILE` | 私钥路径 |
| `PHI_SLURM_PORT` | SSH 端口（默认 22） |

## 6. 关键流程

### 6.1 作业提交流程

```
用户编写 YAML (JobSpec)
    │
    ▼
JobSpec.from_yaml()          # 解析 + validate()
    │
    ▼
SlurmJobManager.submit()
    ├─ sanity check：CPFS 挂载/数据目录存在且非空
    ├─ render_sbatch_script()   # 纯字符串渲染，离线可测
    │     ├─ header（#SBATCH 指令）
    │     ├─ env 展开（${VAR} 从本地环境取，密钥不落 YAML）
    │     └─ srun + torchrun 启动命令
    ▼
SlurmBackend.submit()
    ├─ SSH 登录节点，写入脚本
    ├─ sbatch <script>
    └─ 解析 "Submitted batch job 12345"
    │
    ▼
返回 JobHandle（job_id + spec）
```

### 6.2 状态查询流程

```
status(job_id)
    │
    ├─ squeue -j <id> -h -o %T
    │     ├─ 有输出 → SQUEUE_STATE_MAP 归一 → 返回
    │     └─ 无输出（已结束/不存在）
    │           ├─ sacct -j <id> --format=State,ExitCode
    │           │     ├─ 有记录 → SACCT_STATE_MAP 归一 → 返回
    │           │     └─ 无记录 → UNKNOWN
```

### 6.3 故障自动续训（requeue）流程

```
JobHandle.wait() 轮询
    │
    ▼
发现可重试失败（NODE_FAIL / TIMEOUT / OOM / PREEMPTED...）
    │
    ├─ attempt < max_retries ？
    │     ├─ 是 → 用同一 JobSpec 重提交（job 名加 _r<attempt> 后缀）
    │     │       训练代码读 resume_from 目录自动续训
    │     │       → 新 JobHandle 继续 wait
    │     └─ 否 → 标记 FAILED，触发告警（notify，后续版本）
    │
用户主动 CANCELLED → 不重试，直接返回
```

**训练代码契约**：`--resume <dir>` 存在 checkpoint 则从最近一步续训，否则从头训练。

### 6.4 日志拉取流程

sbatch 的 `--output/--error` 指向 CPFS 日志目录 → 登录节点可读 → SDK 经 SSH `tail -f` 拉取，**无需进计算节点**。

### 6.5 与数据侧的衔接（phi-sync）

```
OSS（数据源）→ NAS 数据流动 Import → CPFS /mnt/cpfs/vla_dataset_v1/
                                             │
                     JobSpec.mounts 挂载进容器 /data
                                             │
                                     训练作业读取
```

提交前 sanity check 保证「数据就绪后才提交」，避免训空数据。

## 7. 接口与配置规范

### 7.1 Python API

```python
from phi_train_slurm import JobSpec, SlurmJobManager, SlurmBackend

spec = JobSpec.from_yaml("examples/exp_vla.yaml")

manager = SlurmJobManager(SlurmBackend(host="login01"))

job = manager.submit(spec)        # → JobHandle
job.wait(timeout=72 * 3600)       # 阻塞到结束（含 requeue）
print(job.status)                 # SUCCEEDED / FAILED / ...
job.logs(follow=True)
job.cancel()
```

### 7.2 YAML 配置示例（VLA 8 节点 × 8 卡）

```yaml
job_name: vla-pretrain-pi0-v1

resource:
  partition: gpu
  qos: normal
  nodes: 8
  gpus_per_node: 8
  cpus_per_task: 16
  mem_per_node_gb: null
  time_limit: "72:00:00"

image: registry-vpc.cn-hangzhou.aliyuncs.com/vla/train:0.1

mounts:
  - /mnt/cpfs/vla_dataset_v1:/data
  - /mnt/cpfs/checkpoints:/ckpt
  - /mnt/cpfs/logs:/logs

env:
  WANDB_API_KEY: ${WANDB_API_KEY}
  OMP_NUM_THREADS: "16"

launch_backend: torchrun

command: |
  train.py --config configs/pi0_v1.yaml --data /data --ckpt /ckpt/vla-pi0-v1

log_dir: /mnt/cpfs/logs

requeue:
  enabled: true
  max_retries: 3
  resume_from: /ckpt/vla-pi0-v1
```

```

```

## 9. 非功能设计说明

| 项 | 设计 |
| --- | --- |
| 零运行时依赖 | 核心链路仅标准库；SSH 用系统 `ssh` 命令；`pyyaml` 为 `[yaml]` extra。wheel 自包含、离线可装 |
| 可移植 | Slurm 交互全部收敛在 `SlurmBackend`，未来换调度器只改 backend |
| 离线测试 | 校验、状态映射、脚本渲染为纯函数，单测不连集群不联网（现有 12 例） |
| 密钥安全 | `${VAR}` 提交时从本地环境展开，缺失即报错（fail-fast），密钥不落 YAML/仓库 |
| 一致性 | JobSpec 可序列化（to_dict/from_dict），requeue 重提交与首次提交用同一 spec |

## 11. 设计权衡与风险

| 项 | 权衡与风险 | 应对 |
| --- | --- | --- |
| Slurm 无原生自动续训 | 需 SDK 自实现 requeue（M4） | 训练代码遵守 `--resume` 契约；重试上限防死循环 |
| SSH 通道 | 每命令一次建连有开销 | 后续可演进为登录节点常驻 HTTP 网关（接口不变，只换 backend） |
| 容器依赖 pyxis | EHPC 未装 pyxis 时容器指令无效 | `image=None` 降级宿主机环境；提交前检测 |
| 小文件 I/O | VLA 数据若为散图，CPFS 读性能差 | 数据侧打包分片（phi_data_sdk 职责） |
| 状态不可见窗口 | 作业结束后 squeue 查不到，需 sacct | status() 双命令兜底已设计 |
